# Project rules

- Event Planner runs on the shared "OTG Shared" Supabase project and signs in through the OTG Control Centre (shared cookie on `.outthereadmin.com.au`, `#sso=` hand-off from tiles). Its tables live in the `eventplanner` schema and helpers in `eventplanner_private`; never create objects in `public`, which belongs to the Control Centre. Who may open the app is the Control Centre `events` tile (`public.app_access`) checked by `eventplanner_private.is_member`.
- Schema changes are new files in `supabase/migrations/`; `supabase/tests/permissions_test.py` must still pass. `supabase/legacy/` holds the old Lovable migrations for reference only.
- AI answers use Claude through `src/lib/ai.server.ts` (`ANTHROPIC_API_KEY`); keep them grounded in retrieved plan text with section/page citations.

- The downloadable user guide PDF is served from `public/out-there-user-guide.pdf` and linked from the Help page; regenerate and replace it whenever app features change, so the in-app guide and PDF stay in sync.
- Event content saves only through the autosave manager in `src/hooks/use-event-saver.tsx` (debounced, per-field version check, keeps failed edits); never add per-field direct writes or a separate "save" button for event values, so status and conflict handling stay correct.
- Event values are keyed by (section id or event-only sub-section id) + field key; never change a field's key on rename/reorder, so saved values stay attached.
- Template sections/fields with saved values are archived (`is_active=false` / `archived_at`), never hard-deleted; a DB trigger blocks deleting sections with values because the value FK cascades.
- Shared-template changes go through admin-checked server functions in `src/lib/admin.functions.ts`; event-only structure lives in `event_custom_fields` / `event_section_extras` under row-level security, so a normal event edit can never change other events.
- Planning coverage rules live in `src/lib/coverage.ts` (with tests); coverage measures entered information only and must never drive event status.
- Date-only values are stored as `YYYY-MM-DD` strings and handled with `src/lib/dates.ts` helpers, never `new Date(str)`/`toISOString()`, to avoid timezone day shifts.
- Uploaded files are stored in the `eventplanner-files` bucket under `event-files/<event id>/<area id>/…`; storage policies use the first folder for event access and the second for area restrictions (older files without an area folder are checked via the value that references them), so keep the path shape.
- Stored files are opened, previewed and downloaded as local blob copies via `src/lib/blob-files.ts`, never by sending the browser to a signed storage URL, because ad blockers block storage links (ERR_BLOCKED_BY_CLIENT).
- Event access (view / edit / manage) is decided only in the database (`eventplanner_private.event_access`, exposed as `my_event_access()` / `event_area_permissions()`); the UI reads it and never re-derives the rules, so screens and RLS can't disagree.
- Area restrictions (`template_sections.restricted_to` default, `event_area_meta.restricted_to` per event) are enforced by RLS via `eventplanner_private.area_of` + `can_read_area` on values, event-only structure, files, document text, pins and change history; any new event-content table must use the same checks.
- "Documents & links" is an index over the `value_links` items of files/links fields — never a second store; item metadata (status, version, revisions, checked_at) lives on the item, items keep a stable `id`, and edits go through the autosave manager.
- Change history (`event_changes`) is written only by database triggers; the client never inserts into it.
- `event_field_values.event_id` has no foreign key to `events`, so deleting an event must delete its values explicitly (as the event menu does).
- Event workspace UI lives in `src/components/event-workspace/` and shares state through `context.tsx`; URL search params (`view`, `area`, `field`, `row`, `edit`, `q`, `scope`, `type`, `doc`, `sec`, `ask`) are the source of truth for what's shown so links and Back work.
- Operations plans live in `ops_documents` / `ops_categories` and the private `eventplanner-ops-plans` bucket, separate from event content: `event_id` NULL = company-wide SOP (staff read via `eventplanner_private.is_staff`), otherwise that event's single overall plan (read by anyone with event access, files under `events/<event id>/…`); writes go through `eventplanner_private.can_write_ops_doc` (admins/leads, or the event's managers). Text is extracted by `indexOpsDocument` (reusing `document-text.server.ts`), sections come from the plan's own contents page (`detectPlanSections` in `src/lib/operations.ts`, falling back to category names) with PDF page offsets, all stored at index time; keyword search uses `search_ops_documents`, each plan is read, searched and asked on its own page `/operations/$docId` (shared `src/components/ops/plan-reader.tsx`, URL `ask`/`sec` params; event pages no longer show plans), and questions are answered by `askOpsPlan` (retrieves passages with `src/lib/ops-ask.ts`, answers only from them, returns section/page citations), so answers stay grounded and checkable.
